# 표·절차 그림을 만드는 결과 계약

세금·지급·절차가 있는 조사에는 별도 요청 없이 이 형식을 적용한다. 채팅에서는 세율 표 → 조건부 지급표 → 절차 안내도 → 규정 확인/사례 재검토 순서로 보여 준다. 저장 요청이나 기존 승인이 있으면 같은 내용을 `sea-entry-record/2`의 `metrics`, `resultView`, `checklist`에 담는다. 채팅의 Markdown 표·Mermaid만 저장하면 웹 지급표·절차 그림이 생기지 않는다.

## 작성 순서

1. **수치 표**: 관련 세율·비용·기한을 `metrics`에 넣는다. 값·단위·기간·정의·공식 근거 번호, 과세표준·납세/징수 주체·적용 조건을 보존한다. 미확인 실제 적용 세율·세액은 별도 지표로 `value:null`, `verificationStatus:"미확인"`과 부족한 자료를 넣는다.
2. **지급표**: 금액·통화·지급 비중을 알고 있고, 세전 지급액에 곱하는 단일 공제 세율을 비교할 때 `resultView.payments`를 만든다. 실제 입력과 계산 가정을 `assumptions`에서 구분한다. 근거를 확인한 일반 세율도 개별 계약 적용이 미정이면 제목을 ‘조건 충족 시 비교’로 쓰고 적용 질문을 별도로 남긴다.
3. **절차 그림**: 해당 업무의 확인한 절차를 순서대로 `resultView.procedures`에 넣는다. 통관·세금 신고·비자·채용·등록 중 실제 요청에 맞는 절차만 선택한다. 채팅에서는 같은 단계로 짧은 Mermaid 또는 화살표 안내도를 제공한다. 각 단계의 담당·업무·서류·시점·근거를 함께 남긴다.
4. **재검토**: 규정 수치 확인과 사례 적용 확인을 구분한다. 남은 적용 질문은 `checklist`의 미확인/충돌 항목, 부족한 수치는 null 지표, 상충 근거는 `conflicts`, 다음 행동은 `nextActions`에 넣는다. 담당·필요 자료·실행 전 시점·확인 전 보류할 행동을 명시한다. 법률 항목의 `legalEvidence`에는 실제 조문·현행성·적용 이유·남은 질문을 담는다. 확인 상태에 빈 근거 장부를 붙이면 저장 검증에 실패한다.
5. **저장 확인**: `save_research` 성공 뒤 `get_research`로 다시 읽어 해당 카드의 `metrics`, 지급 시나리오, 절차 단계·근거, 재검토 항목이 보존됐는지 확인한다. 저장 실패·필드 누락은 복구하거나 구체적으로 알린다. 실제 성공 응답 없이 웹 표시·저장 완료를 말하지 않는다.

## 금액·세율이 부족한 경우

| 상황 | 출력과 저장 |
| --- | --- |
| 금액·통화·비중 미정 | 지급 계산 보류 사유와 필요한 질문을 보여 준다. `payments`는 생략한다. 세액 null 지표·재검토 항목은 남긴다. 가상의 1억 원이나 30/30/40을 기본값으로 넣지 않는다. |
| 금액·비중은 알려졌고 세율만 미확인 | 해당 세율 지표를 null로 연결한 지급 시나리오는 저장 가능하다. 웹은 ‘계산 보류’로 표시한다. 미확인을 0%로 바꾸지 않는다. |
| 사용자가 계산 예시를 요청 | 예시 총액·통화·비중과 가정임을 명시한다. 근거 확인된 단일 공제 세율로만 조건부 비교한다. 실제 금액으로 표시하지 않는다. |
| 법인세(이익 기준)·누진 근로소득세·VAT·복합 세목 | 지급액 × 한 세율로 대신 계산하지 않는다. 세목별 과세표준·구간·공제·공식 계산식을 수치 표에 남기고, 필요한 입력을 질문한다. 현재 지급표는 단일 대금 공제 비교만 지원한다. |
| 근거·공식 절차 미확인 | 추정 절차를 확정 그림으로 만들지 않는다. 확인 전 필요한 자료·담당·질문을 남기고, 근거가 있는 단계까지만 ‘부분 안내’로 표시한다. |

서버는 A/B 등급·확인일·현행 표시·근거와 숫자가 확인된 `%` 지표를 연결한 지급표만 계산한다. 재검토 기한이 도래하면 계산을 보류한다. 이 형식 검증은 실제 법률 검증을 대신하지 않는다.

## 저장 필드

선택 필드 `resultView`는 아래 키만 사용한다. 기존 카드의 `resultView.visa`도 동일한 절차 객체로 계속 읽힌다. 새 카드에는 `procedures`를 쓰며 같은 절차를 visa와 procedures 양쪽에 중복 저장하지 않는다. 해당 결과가 없으면 필드를 생략한다.

| 필드 | 형식·제한 |
| --- | --- |
| payments | 시나리오 배열, 최대 4개 |
| payments[].title / assumptions | 비어 있지 않은 문자열, 각각 200/3000자 이하 |
| payments[].amount / currency | 세전 비교 총액 숫자 0~1조 / 대문자 ISO 통화 코드 3자 |
| payments[].rateMetric | 같은 카드 `metrics[].name`과 정확히 일치하는 이름, 300자 이하. 이름이 유일해야 계산 가능 |
| payments[].installments | 1~12개. label은 1~100자, share는 0 초과~100 이하 숫자, 합계 100% |
| procedures | 절차 객체 배열, 최대 4개 |
| procedures[].title / caveat | 비어 있지 않은 문자열, 각각 200/3000자 이하. caveat에 선행 조건·보류 이유 |
| procedures[].steps | 1~10단계. 너무 길면 사용자 목적에 맞는 주요 단계로 묶는다 |
| steps[].title / owner | 비어 있지 않은 문자열, 각각 150/200자 이하 |
| steps[].action / documents | 비어 있지 않은 문자열, 각각 3000자 이하. action에 완료 증빙도 포함 |
| steps[].timing | 비어 있지 않은 문자열, 500자 이하. 법정 기한·공식 처리 기준·평균을 구분. 미확인은 그대로 표시 |
| steps[].sourceRefs | 같은 카드 sources에 존재하는 중복 없는 양의 정수 1~30개 |

서류·시점이 미확인이면 ‘미확인 — 확인처/필요 자료’를 문자열로 쓴다. 담당이 제안이면 ‘제안 담당’으로 표시한다. 출처 등급·접속 성공만으로 현행성·적용 상태를 확인 처리하지 않는다. 최종 결론은 비워 두고 `conclusionConfirmed:false`로 저장한다.

`../../` 같은 상대 경로를 결과 JSON에 넣지 않는다. 정확한 기본 카드·법률 근거 필드는 `../skills/research-record/references/record-schema.md`, 실제 연결 절차는 `live-workflow.md`를 따른다. 연결이 없으면 위 필드를 포함한 JSON을 제공하고 아직 저장되지 않았음을 알린다.
